# Requirements Review 2026-09-10

English | [中文](2026-09-10.zh.md)

## Summary

Scope note: this dated package records the 2026-09-10 review agenda and proposed slices. For product direction and the current implementation order, use [Harness Engineering Product Direction](../harness-engineering.md) and [the backlog](../backlog.md#implementation-order). The proposals below do not override that order; the added `REQ-HARNESS-001`–`005` are outside this package's original inventory.

This review package organizes the current HuntianLing product requirements for a formal requirement review. It covers the 77 unique `REQ-*` ids in [../backlog.md](../backlog.md) and the workflow-specific design material in [../../architecture/workflow-orchestration-engine.md](../../architecture/workflow-orchestration-engine.md).

The review goal is to decide whether each requirement is clear, complete, testable, correctly scoped, and ready to become tracked WorkItems. The review should also approve the next implementation slice and record any requirement splits, blockers, open decisions, or rejected assumptions.

## Review Objectives

- Confirm that `docs/requirements/backlog.md` is the product requirement source for implementation.
- Confirm that the internal board remains the source of truth and does not depend on GitHub.
- Validate the requirement hierarchy, milestone model, and cross-milestone delivery model.
- Validate the split between board data, workflow orchestration, Agent Team Chat, SCM/CI evidence, and governance records.
- Confirm that every requirement can be reviewed, split, prioritized, assigned, tested, and audited.
- Identify requirements that are too large, ambiguous, missing acceptance criteria, missing APIs, or missing evidence rules.
- Decide the first implementation slice and the sequence for later slices.

## Review Scope

In scope:

- All requirements in [../backlog.md](../backlog.md).
- Workflow orchestration design in [../../architecture/workflow-orchestration-engine.md](../../architecture/workflow-orchestration-engine.md).
- Requirement hierarchy, Milestones, delivery slices, boards, APIs, storage, authentication, intake, Agent/Skill model, team workflow, Team Chat, SCM/CI, governance, Web UI, and audit.
- Implemented baseline requirements and planned requirements.

Out of scope:

- Legal interpretation of which laws apply to a real customer.
- Final selection of every technology library for the visual workflow designer.
- Final workflow DSL syntax.
- Production infrastructure sizing.
- Exhaustive implementation estimates for every future WorkItem.

## Entry Criteria

- The English and Chinese documentation pairs pass `pnpm run doc-sync`.
- Every requirement has a stable `REQ-*` id or is recorded as a review finding.
- Reviewers can access [../backlog.md](../backlog.md), [../backlog.zh.md](../backlog.zh.md), [../../architecture/workflow-orchestration-engine.md](../../architecture/workflow-orchestration-engine.md), and [../../architecture/workflow-orchestration-engine.zh.md](../../architecture/workflow-orchestration-engine.zh.md).
- Open decisions from the workflow design are visible to reviewers.
- The review owner prepares a disposition column for each requirement.

## Exit Criteria

Each reviewed requirement must receive one disposition:

| Disposition | Meaning |
| --- | --- |
| `accepted` | The requirement is clear enough to become implementation work. |
| `accepted_with_changes` | The requirement is valid, but the backlog must be updated before implementation. |
| `split_required` | The requirement is too large or mixes concerns and must be decomposed. |
| `blocked` | The requirement depends on an unresolved product, technical, security, legal, or operational decision. |
| `deferred` | The requirement is valid but outside the approved implementation slice. |
| `rejected` | The requirement should not remain in the backlog. |

The review is complete only when:

- Every `REQ-*` id has a disposition.
- Every `accepted_with_changes`, `split_required`, or `blocked` item has an owner and next action.
- The first implementation slice has approved scope, dependencies, and success checks.
- Backlog updates are applied to both language versions and re-recorded with `pnpm run doc-sync:write`.

## Review Checklist

Use this checklist for every requirement domain.

- Does each requirement have a clear user, system actor, or project role?
- Is the requirement small enough to implement, or does it need decomposition?
- Are parent-child relationships and cross-milestone delivery rules explicit?
- Are acceptance criteria observable and testable?
- Are suggested APIs complete enough to support internal service calls and HTTP calls?
- Is the data owner clear: board, workflow engine, Team Chat, SCM/CI adapter, evidence store, or governance pack?
- Does the requirement run without GitHub as a hard dependency?
- Are project-level permissions and role boundaries specified for write actions?
- Does the requirement identify required evidence before marking work delivered?
- Can the requirement be shown in board views, workflow views, or reports?
- Does the requirement need bilingual documentation or user-facing localized text?
- Does implementation require new Skills, tools, adapters, migrations, or UI surfaces?

## Workflow-Specific Checklist

Use this checklist for `REQ-FLOW-*`, `REQ-AGENT-*`, `REQ-TEAM-*`, and `REQ-COLLAB-*`.

- Does the workflow node bind to role first and concrete member second?
- Does the node declare required Skills, allowed tools, inputs, outputs, checks, and evidence?
- Does the scheduler have enough state to decide ready, queued, delayed, blocked, retried, reassigned, or cancelled?
- Does every role handoff require both an accepted event and an accepted state transition?
- Does Agent Team Chat expose collaboration work without replacing the board or normal LLM task chat?
- Can humans interrupt, approve, reject, redirect, or stop high-risk Agent actions?
- Can Workflow Test Lab simulate the happy path and failure paths?
- Can the visual workflow designer show static structure before runtime?
- Can runtime visualization explain scheduler decisions and blockers?
- Are custom events, custom nodes, and extension points constrained by schemas, permissions, tests, and conformance reports?

## Preliminary Review Findings

These findings should be confirmed or revised during the review.

| Finding | Impact | Recommended decision |
| --- | --- | --- |
| The backlog is comprehensive but too large for one implementation slice. | Without slicing, implementation can drift across unrelated surfaces. | Approve an MVP slice and defer the rest with explicit dependencies. |
| Workflow orchestration has 21 requirements and several open decisions. | The engine could become the largest risk area. | Implement template/version/state foundations before visual editing and third-party extension packs. |
| Database, authentication, and audit are prerequisites for external Web access. | External users and regional OAuth cannot be safely enabled on the JSON baseline. | Treat SQLite/PostgreSQL, sessions, permissions, and audit as foundation work. |
| Agent capability boundaries and state recognition are security-critical. | Agents could otherwise act beyond role, stale state, or missing approval. | Require these before Git push, PR creation, CI trigger, merge, or deployment actions. |
| Skills cannot be universal by default. | The AI team cannot truthfully claim domain coverage. | Require project skill coverage scan and Skill Gap WorkItems before Agent task execution. |
| SCM and CI adapters are necessary for evidence-based delivery. | The system cannot verify code delivery without branch, diff, review, and CI evidence. | Pick one first adapter path and make all others adapter-compatible. |
| Governance requirements need explicit human ownership. | The product must not make legal determinations. | Assign compliance/legal owners and keep obligation selection as an approved project decision. |
| Team Chat must remain a collaboration log, not a hidden task runner. | Confusing it with normal LLM task chat would obscure accountability. | Keep collaboration tasks as internal project records with visible state transitions. |

## Proposed First Implementation Slice

The first slice should prove the internal requirement lifecycle before adding advanced workflow automation.

Recommended scope:

- `REQ-DATA-001`: database service with SQLite first and PostgreSQL abstraction.
- `REQ-REQ-001`, `REQ-BOARD-003`, `REQ-BOARD-004`: requirement authoring, APIs, and decomposition traceability.
- `REQ-MILESTONE-002`: delivery slices for cross-milestone parent requirements.
- `REQ-AUDIT-001`: audit records for requirement, milestone, and transition changes.
- `REQ-AUTH-001`, `REQ-AUTH-002`: local authenticated Web/API access and safe password hashing.
- `REQ-WEB-002`: authenticated Web UI foundation.

Defer from the first slice:

- Third-party OAuth providers beyond the auth adapter interfaces.
- Full workflow visual designer.
- Workflow Test Lab replay UI.
- All SCM/CI providers beyond the internal adapter contracts.
- Governance control pack implementation beyond the data model and evidence hooks.

## Review Outputs

The review should produce:

- A disposition for each `REQ-*` id.
- A list of approved requirement splits.
- A first implementation slice with dependencies and owners.
- A list of blocked decisions with named owners.
- A list of missing Skills and missing tools.
- API changes that must be reflected in backlog acceptance criteria.
- Data entities that must be promoted into migrations.
- Evidence and gate rules required before delivery.
- Updates to [../backlog.md](../backlog.md) and [../backlog.zh.md](../backlog.zh.md).

## Follow-Up Rules

- Backlog edits must update both language versions and pass `pnpm run doc-sync`.
- Implementation tasks must name affected `REQ-*` ids.
- Requirement splits must keep parent-child traceability and acceptance coverage.
- Deferred requirements must remain visible with their dependency or reason.
- Review decisions that affect workflow behavior must also update [../../architecture/workflow-orchestration-engine.md](../../architecture/workflow-orchestration-engine.md) and its Chinese counterpart.
- Every accepted first-slice requirement must have at least one focused validation plan before coding starts.
