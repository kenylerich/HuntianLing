# 需求评审 2026-09-10

[English](2026-09-10.md) | 中文

## 摘要

范围说明：本日期评审包记录 2026-09-10 的评审议程和拟议切片。产品定位与当前实现顺序以 [Harness Engineering 产品定位](../harness-engineering.zh.md) 和 [backlog](../backlog.zh.md#实现顺序) 为准。下文提案不覆盖该顺序；新增的 `REQ-HARNESS-001`–`005` 不属于本评审包的原始清单。

本文档把当前 HuntianLing 产品需求组织成一次正式需求评审包。评审范围覆盖 [../backlog.zh.md](../backlog.zh.md) 中 77 个唯一 `REQ-*` 需求编号，以及 [../../architecture/workflow-orchestration-engine.zh.md](../../architecture/workflow-orchestration-engine.zh.md) 中的工作流专项设计内容。

评审目标是判断每个需求是否清晰、完整、可测试、范围正确，并且是否可以转成看板中的 WorkItems。评审还要批准下一批实现范围，并记录需求拆分、阻塞、待决问题或被拒绝的假设。

## 评审目标

- 确认 `docs/requirements/backlog.md` 是实现时的产品需求来源。
- 确认内部看板仍然是事实源，并且不依赖 GitHub。
- 验证需求层级、里程碑模型和跨里程碑交付模型。
- 验证 board data、workflow orchestration、Agent Team Chat、SCM/CI evidence 和 governance records 的职责拆分。
- 确认每个需求都可以被评审、拆分、排序、分配、测试和审计。
- 识别过大、含糊、缺少验收标准、缺少 API 或缺少证据规则的需求。
- 决定首个实现切片以及后续切片顺序。

## 评审范围

范围内：

- [../backlog.zh.md](../backlog.zh.md) 中所有需求。
- [../../architecture/workflow-orchestration-engine.zh.md](../../architecture/workflow-orchestration-engine.zh.md) 中的工作流编排设计。
- 需求层级、Milestones、delivery slices、boards、APIs、storage、authentication、intake、Agent/Skill model、team workflow、Team Chat、SCM/CI、governance、Web UI 和 audit。
- 已实现基线需求和计划需求。

范围外：

- 对真实客户适用哪些法律的法律解释。
- 可视化工作流设计器所有技术库的最终选择。
- 最终 workflow DSL 语法。
- 生产基础设施容量规划。
- 每个未来 WorkItem 的完整实现估算。

## 进入条件

- 中英文文档配对通过 `pnpm run doc-sync`。
- 每个需求都有稳定 `REQ-*` id，或被记录为评审发现。
- 评审者可以访问 [../backlog.md](../backlog.md)、[../backlog.zh.md](../backlog.zh.md)、[../../architecture/workflow-orchestration-engine.md](../../architecture/workflow-orchestration-engine.md) 和 [../../architecture/workflow-orchestration-engine.zh.md](../../architecture/workflow-orchestration-engine.zh.md)。
- 工作流设计中的 open decisions 对评审者可见。
- 评审负责人为每个需求准备 disposition column。

## 退出条件

每个已评审需求必须得到一个 disposition：

| Disposition | 含义 |
| --- | --- |
| `accepted` | 需求已经清晰到可以进入实现。 |
| `accepted_with_changes` | 需求有效，但实现前必须先更新 backlog。 |
| `split_required` | 需求过大或混合多个关注点，必须拆分。 |
| `blocked` | 需求依赖未解决的产品、技术、安全、法律或运维决策。 |
| `deferred` | 需求有效，但不在已批准实现切片中。 |
| `rejected` | 需求不应继续保留在 backlog。 |

只有满足以下条件，评审才算完成：

- 每个 `REQ-*` id 都有 disposition。
- 每个 `accepted_with_changes`、`split_required` 或 `blocked` 项都有 owner 和 next action。
- 首个实现切片有批准范围、依赖和成功检查。
- backlog 更新同步应用到中英文版本，并用 `pnpm run doc-sync:write` 重新记录配对。

| 20 min | 产品模型：Project、WorkItem hierarchy、Milestone、delivery slice | 对需求树和跨里程碑模型作出决策。 |
| 20 min | Board、Web、intake、需求分析和设计 | 识别 authoring、chat intake、attachments 和 APIs 的缺口。 |

## 评审检查清单

每个需求域都使用这个清单。

- 每个需求是否有清晰 user、system actor 或 project role？
- 需求是否足够小，可以实现；还是需要拆分？
- 父子关系和跨里程碑交付规则是否明确？
- 验收标准是否可观察、可测试？
- 建议 APIs 是否足够支撑 internal service calls 和 HTTP calls？
- 数据 owner 是否清楚：board、workflow engine、Team Chat、SCM/CI adapter、evidence store 或 governance pack？
- 需求是否能在不依赖 GitHub 的情况下运行？
- 写操作的 project-level permissions 和 role boundaries 是否指定？
- 需求是否说明进入 delivered 前需要哪些 evidence？
- 需求能否显示在 board views、workflow views 或 reports 中？
- 需求是否需要双语文档或用户可见本地化文本？
- 实现是否需要新的 Skills、tools、adapters、migrations 或 UI surfaces？

## 工作流专项检查清单

`REQ-FLOW-*`、`REQ-AGENT-*`、`REQ-TEAM-*` 和 `REQ-COLLAB-*` 使用这个清单。

- workflow node 是否先绑定 role，再绑定 concrete member？
- node 是否声明 required Skills、allowed tools、inputs、outputs、checks 和 evidence？
- scheduler 是否有足够 state 判断 ready、queued、delayed、blocked、retried、reassigned 或 cancelled？
- 每次 role handoff 是否都要求 accepted event 和 accepted state transition？
- Agent Team Chat 是否暴露协作工作，同时不替代 board 或普通 LLM task chat？
- humans 是否可以 interrupt、approve、reject、redirect 或 stop 高风险 Agent actions？
- Workflow Test Lab 是否能模拟 happy path 和 failure paths？
- visual workflow designer 是否能在 runtime 前展示 static structure？
- runtime visualization 是否能解释 scheduler decisions 和 blockers？
- custom events、custom nodes 和 extension points 是否被 schemas、permissions、tests 和 conformance reports 约束？

## 初步评审发现

这些发现需要在评审会上确认或修订。

| 发现 | 影响 | 建议决策 |
| --- | --- | --- |
| backlog 覆盖面完整，但对一个实现切片来说过大。 | 如果不切片，实现会横跨太多无关 surface。 | 批准 MVP slice，其余需求带明确依赖 deferred。 |
| workflow orchestration 有 21 个需求和多个 open decisions。 | 引擎可能成为最大风险区域。 | 先实现 template/version/state 基础，再做 visual editing 和 third-party extension packs。 |
| database、authentication 和 audit 是外部 Web 访问的前置条件。 | JSON baseline 不适合安全开放给外部用户。 | 把 SQLite/PostgreSQL、sessions、permissions 和 audit 作为 foundation work。 |
| Agent capability boundaries 和 state recognition 是安全关键能力。 | 否则 Agent 可能越权、基于 stale state 或缺少 approval 行动。 | Git push、PR creation、CI trigger、merge 或 deployment 前必须先完成这些能力。 |
| Skills 不能默认全能。 | AI 团队不能真实声称覆盖所有领域。 | Agent task execution 前要求 project skill coverage scan 和 Skill Gap WorkItems。 |
| SCM 和 CI adapters 是证据式交付的必要条件。 | 没有 branch、diff、review 和 CI evidence，系统无法验证代码交付。 | 选择首个 adapter 路径，并让其他 adapters 兼容同一内部模型。 |
| Governance requirements 需要明确 human ownership。 | 产品不能作法律判断。 | 指定 compliance/legal owners，并把 obligation selection 作为已审批项目决策。 |
| Team Chat 必须保持协作日志定位，而不是隐藏任务运行器。 | 若混同普通 LLM task chat，会削弱责任追踪。 | collaboration tasks 作为内部 project records，并带可见 state transitions。 |

## 建议首个实现切片

首个切片应先证明内部需求生命周期，再增加高级工作流自动化。

建议范围：

- `REQ-DATA-001`：database service，先支持 SQLite，并保留 PostgreSQL 抽象。
- `REQ-REQ-001`、`REQ-BOARD-003`、`REQ-BOARD-004`：需求编写、APIs 和拆分可追踪。
- `REQ-MILESTONE-002`：支持跨里程碑父需求的 delivery slices。
- `REQ-AUDIT-001`：记录 requirement、milestone 和 transition 变更审计。
- `REQ-AUTH-001`、`REQ-AUTH-002`：本地认证 Web/API 访问和安全密码哈希。
- `REQ-WEB-002`：authenticated Web UI foundation。

首个切片暂缓：

- auth adapter interfaces 之外的三方 OAuth providers。
- 完整 visual workflow designer。
- Workflow Test Lab replay UI。
- internal adapter contracts 之外的所有 SCM/CI providers。
- data model 和 evidence hooks 之外的 governance control pack implementation。
